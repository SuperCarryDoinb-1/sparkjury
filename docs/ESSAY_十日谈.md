# DGX Spark 黑客松十日谈：给 Agent 做体检的 Agent

> 第三届 NVIDIA DGX Spark 黑客松 · Agent Skills 开发挑战赛，队伍「能工智人5X」。作品 SparkJury 开源在 https://github.com/VioletScar-Hui/sparkjury 。这篇按天记录十天里做了什么、踩了什么坑、哪些取舍现在看是对的。

## 第一天 9 月 20 日 · 开赛

训练营回放看完，赛题一句话："从会回答走向能完成"。组里五个人，两个产品、三个技术，云节点是一台 DGX Spark，128 GB 统一内存。第一反应是做个会干活的 Agent，第二反应是：我们公司已经有一堆会干活的 Agent，没人知道它们干得好不好。

## 第二天到第四天 9 月 21 日到 23 日 · 调研

把方向摊开：营销 Skill 路由（有真数据，但脱敏是坑）、个人数字分身、自迭代评测 Agent。调研报告写了一万六千字，结论三条：

1. 评测是普遍缺口。LangChain 的调研，89% 的团队有可观测，30% 完全不评测。
2. 市面上能自动归因的产品全是云 SaaS；开源自托管的只给工具箱。"本地 + 开箱即用 + 告诉你先修哪个"没人做。
3. 两个坑要绕开：自动定位根因不可靠（前沿模型 5% 到 25%），多个裁判必须来自不同家族（九个前沿 judge 只有两票独立）。

还查清了会上说的那个"Jeff"是 TypeSafe 的 Jev，9 月 21 日刚开放，只有云 API，装不进 DGX。端云协同的讲法要改：本地跑开源裁判，云端只仲裁分歧。

## 第五天 9 月 24 日 · 定方向

对齐会。被评对象定为 τ²-bench retail，公开、有金标、评委看得懂；真实营销场景做故事。产品一句话：一台 DGX Spark，顶一个评测组。四步：排除环境失败、三家裁判打分、分歧仲裁、聚类出卡片。不做的三件事写进文档：不承诺根因，不让 Agent 自己打分自己改，不重做 trace 采集。

## 第六天 9 月 25 日 · PRD 与分工

PRD、架构图、流程图。分工：万凌 Skill 库，千富 PRD 与真实数据，人瑜定位与选型，剑乔前端，滨辉 Harness 与部署。

## 第七天 9 月 26 日 · 一天十个模块

把方案拆成 11 个模块，按"数据契约先行、每步可离线测试"排序，一个模块一个模块地建，每个带自测和验收命令：

- M1 统一 Trace 模型，τ²-bench 和 OTel 两个适配器，SQLite。
- M2 七条确定性规则标环境失败。有意思的一条：工具返回"permission denied: user not authenticated"不算环境问题，那是 Agent 自己跳过了认证。
- M3 三裁判面板，四份 rubric，OpenAI 兼容客户端加规则裁判兜底。
- M4 Jev 仲裁，接口按官方文档写，三层降级。
- M5 聚类：HDBSCAN 为主，样本太少自动退回凝聚聚类；标签从 MAST 和 TRAIL 压成十类。
- M6 证据卡片和回归对比，成对比较交换顺序跑两遍。
- M7 编排器：状态机、运行清单、事件总线、自动降级。
- M8 FastAPI 加 SSE，一个自包含的 Cockpit 页。
- M9 六个 Agent Skills 按规范打包，NeMo Agent Toolkit 评估器插件。
- M10 DGX 部署脚本、τ²-bench 跑数脚本、API 令牌。

当晚 96 个测试全绿（到 9 月 29 日早上这个数字是 319 passed、3 skipped，模块还在往上加），`sparkjury run --demo` 两秒跑完，卡片上写着"先修：未验证身份就执行写操作"。

教训一条：Windows 终端的 GBK 编码把箭头和圆点全变成乱码，CLI 输出改成纯 ASCII 才安生。

## 第八天 9 月 26 日夜到 27 日 · 上节点

SSH 进去第一件事是看队友留下了什么：组委会预装了 vLLM 0.28，队友已经下了一个 52 GB 的密集 27B 和一个 21 GB 的 Nemotron-3.5-Lightning（NVIDIA 自家 MoE，NVFP4）。原计划的 Gemma 当场换成 Nemotron：第二个家族、省一次下载、平台分更高。

第一次同时起两个裁判，bf16 版 Qwen3-30B（57 GB）和 Nemotron 一起把 119 GB 统一内存打爆，内核 OOM 连 tmux 会话带整个用户登录一起杀了，日志里只剩一句 "A process of this unit has been killed by the OOM killer"。换成 FP8 版（31 GB），显存比例总和压到 0.73，开 linger，服务全部脱离 tmux 用 setsid 跑，之后再没掉过。

Nemotron 当裁判的第一轮，52 票错 10 票：它把推理过程当正文往外吐，600 个 token 用完了 JSON 还没出来。关掉 thinking 之后 0 错，2.3 秒一票。Qwen3-30B-A3B-FP8 是 7 秒一票，52 票 0 错。两家一致率 76.9%，三条 trace 进仲裁。它们给的理由是这样的：

> 用户明确要求改的是某个订单的收货地址，Agent 却两次修改了用户档案的地址，用户在第 9 步纠正之后 Agent 又做了一遍同样的操作。

规则标签器一开始把这簇标成 loop，因为它是按 mock 裁判的措辞写的。改成具体类别优先之后，卡片上是 wrong_tool 3 条、unauthenticated_action 2 条，和样本里埋的坏例一致。

零碎的坑：节点到 GitHub 和 PyPI 都慢，uv 卡在下托管版 Python 上七分钟，换系统 Python 加清华镜像一分钟同步完；Windows 上写出来的脚本全是 CRLF，bash 报 `$'\r': command not found`；`pkill -f` 的模式会匹配到自己所在的命令行，把自己杀了两次；SSH 网关会掐闲置几分钟的连接，长任务只能放 tmux。tau2-bench 的 git clone 反复 early EOF，最后从镜像下了源码 zip；它的 `--save-to` 是名字不是路径。

零售任务的 system prompt 很长，8k 上下文直接 ContextWindowExceeded，被评 Agent 和模拟用户都改成 32k。30 任务 x 3 次的完整跑数在凌晨启动，6 路并发，一个任务大约 8 分钟。

## 第九天 9 月 28 日 · 闭环

白天是并行推进：滨辉把 90 条真批跑完的判卷环合了进来，金标不再进裁判 prompt，审计只审真裁判；万凌把六个 Skill 的端到端用例先写红再修绿；千富交了真实舆情场景的脱敏 trace。我这边是看板：早上刚接受协作者邀请，第一版按参考图把看板重做成白底细线、黑主按钮、大数字 KPI 的样子。

晚上十点开了半小时会，把方向收紧了。产品负责人一句话定了调："我基本不看那些数，我只要知道我该调啥、怎么调、哪里有问题。"前端的 P0 被压成三样：北极星指标（可用率）、分场景错误原因及占比、典型错误 case 归因卡片；trace 原文备注、动态归因检索这些 P1 时间不够就往后放。另一句共识是"先跑通、看得过去，再打磨"，明天 24 点前必须提交。

会后按纪要把看板首页改成"调优报告"：可用率 64px 大数，黑卡直接写"先修什么"和"怎么改"，分场景表按可用率从低到高排、最差的排最前。改完凌晨合进 main，节点主树同步，公网看板换新。

## 第十天 9 月 29 日 · 三家族齐活，推倒重来

早上先回答一个心里一直没底的问题：step-3.7-flash 和 Jev 到底用上了没有。查节点上留的真跑记录，答案是都没有——StepFun 那次是 401 退化成 mock，Jev 一直没 key。两个 key 现在都在节点的共享 .env 里了，于是用 `deploy/run.node.toml` 真跑一轮。

结果一半好一半坏。Jev 是通的：52 个维度裁决全部由 Jev 给出，降级为零，簇标签也是它打的，这是仓库里第一份真 Jev 数据。StepFun 却 52 次调用全部 HTTP 402，账户额度用完了。更有意思的是它带出的一个产品问题：第三裁判全错并不会进 manifest 的降级列表，只体现在错票数和一致率上——错票按分歧计，一致率被打到 0%，52 个维度全部送仲裁。看板上看不出第三裁判其实没参与。换了一个有额度的 key 重跑，三家族第一次齐活：Qwen 52 票 0 错 3.7 秒，Nemotron 52 票 0 错 3.6 秒，step-3.7-flash 52 票 2 错 9.5 秒（那 2 票是思维模型把 JSON 夹在散文里，强制 JSON 输出的补丁能清零）；三票一致率 30.8%，9 条 trace 进仲裁，Jev 裁了 13 个维度，与基准金标一致率 92.3%，6 个 badcase 聚成 3 类。真裁判比 mock 多挑出了一类"编造事实"，第三个家族确实带来了不同视角。

然后是看板的第二次推倒重来。前一版被评"太素，不了解项目的人看不出这是干嘛的"，于是按一张 SaaS 参考图整体重做：九页工作台，首页一句话说明产品、上传 Trace 和新建评测任务两个入口、四张带趋势线的 KPI、随任务实时点亮的六步流程、失败类型环图、四维 × 三裁判 + 仲裁结果的得分柱图。为了让"上传 Trace → 新建任务"和"各维度得分"真的接上后端，补了两条接口：`POST /uploads` 和 `GET /runs/{id}/scores`。加路由就得同步架构文档的路由表、模块用例数和四处总测试数，否则验收证书会红——这套"文档数字不许手抄"的机制在最后一天又抓了一次。Playwright 把九页逐页跑了一遍，上传样本、新建任务、点 trace 看裁判理由、簇展开、回归对比、决策弹窗，零报错；三平台 CI 绿了合并，节点主树同步，这次改了后端，把跑在 tmux 外的旧 api 进程停掉，按部署脚本的写法在 tmux 里重新拉起。319 个测试、54 条证书断言，全绿。

回头看十天的取舍。对的：把评测对象定在有金标的 τ²-bench，让"裁判判得对不对"本身可验证；三个家族而不是三个 Qwen；不承诺根因、只给聚类和证据、人来拍板；每一次降级都写进 manifest 并亮在看板上，包括我们自己不光彩的那次 402。要改的：一致率把错票按分歧计，第三裁判缺席时数字会失真，应该把"某裁判错票率超阈值"也记为降级；step-3.7-flash 作为思维模型，输出预算和 JSON 强制应该一开始就按它的脾气配，而不是等真批里废掉 17 个判定才发现。

## 写在最后

评测 Agent 最难的不是打分，是分清什么不该打分：环境的错不算 Agent 的，三票一致的不用仲裁，聚类出来的不是根因。把边界写在卡片上，比多做一个功能更值钱。

十天里最有用的一个习惯是让文档里的每个数字都能被机器核对。README 写 319 个测试，证书就真跑一遍数出来；路由表多写一条少写一条都红。人在截止日前不会去数、去翻，但 CI 会。
